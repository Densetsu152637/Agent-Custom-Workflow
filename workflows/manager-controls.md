# Manager process controls

Managers: load before dispatch and when configuring, monitoring or changing process/iteration limits and handling checkpoints. These are mandatory controls when directing descendants; they are not required for leaf execution.

## Process and iteration controls

1. Inspect documented host/tool controls before dispatch. Configure supported concurrency/depth, turn/tool-call limits, execution timeouts, and cancellation controls where applicable; do not invent APIs or introduce a standalone runtime to enforce this workflow. A polling/wait timeout bounds observation only unless the tool documents that it stops execution.
2. Record enforceable limits, monitored allowances, unavailable controls and supported cancellation in the manager's dispatch record. Send the child its actionable limits, iteration unit/allowance or bounded milestone, checkpoint and stop instructions; identify which are enforced versus monitored. Omit irrelevant unavailable-control lists from child briefs. Recovery retries follow [stalls and recovery](../guides/subagent-recovery.md#stalls-and-recovery); iteration allowances cannot reset them.
3. If the host lacks a required control, use the immediate manager's active-child count, observed iterations, bounded tool calls, and milestone checkpoints as the fallback. Inspect progress at checkpoints, stop dispatching when an allowance is reached, and stop/cancel or redirect running work through available controls. If cancellation is unavailable, request a stop, report the limitation, and verify write/process cessation before transferring ownership. Prompt instructions are monitored requests, not runtime enforcement.
4. Review the returned result at the checkpoint. Continue only within remaining scope/allowance, or repair scope and obtain any required budget authority under [recovery](../guides/subagent-recovery.md#stalls-and-recovery). A stopped process or exhausted allowance is incomplete until acceptance evidence establishes otherwise.
